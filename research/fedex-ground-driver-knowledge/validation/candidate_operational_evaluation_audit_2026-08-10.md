# Candidate operational evaluation audit

Status date: 2026-08-10

## Purpose and design

Sixty-nine development prompts from the owner-supplied candidate pack were independently mapped to canonical Ready Route operational records. Candidate expected answers were not used as authority. Every gold case carries canonical knowledge IDs, information sufficiency, response mode, required clarification, prohibited behavior, and source candidate trace.

The evaluated prompts are not added to `driver_question_variants`, the formal 192-case retrieval index, or any record pattern. The baseline therefore measures generalization from the maintained knowledge surfaces rather than exact-prompt memorization. All 32 deterministic holdout prompts remain untouched.

## Baseline result

| Measure | Result |
| --- | ---: |
| Reviewed development cases | 69 |
| Top-1 canonical match | 57 |
| Top-5 canonical match | 69 |
| Production response-mode match | 69 |
| Correct publication-withheld escalations | 11 |
| Unsafe answer-gating failures | 0 |
| Retrieval failures | 0 |
| Response-mode failures | 0 |

The exact deterministic result is preserved in `validation/candidate_operational_retrieval_results.json` and regenerated by `npm --prefix backend run knowledge:validate-candidate-retrieval`.

## Remediation result

The first 69-case run produced 13 top-five retrieval failures and 20 response-mode failures across active-threat versus accident reporting, generic signature language, leak/damage language, pickup-ready state, generic release requests, mailbox placement, FORGE login/sync, ID-controlled delivery, roadway obstruction, term definitions, and ambiguous call-tag/hazmat/device questions. It also exposed one unsafe answer-gating failure: `business closed can i leave it` selected the eligible administrative closure-message workflow even though the package-release procedure is not production eligible.

The remediation changed general language normalization, intent scoring, explicit ambiguity detection, definition handling, and status-boundary logic. It did not add candidate prompts to record variants, patterns, or the retrieval index. The resulting suite has no top-five retrieval failure, no response-mode failure, and no unsafe gating failure. Top-1 remains 57/69, which is acceptable for multi-record and clarification cases because every expected record appears in the top five and the production behavior is correct. The maintained 192-case suite remains 192/192.

Four permanent focused regression tests cover the closure-message/package-disposition boundary, FORGE outage-versus-compliance ambiguity, generic release clarification, and concise canonical term definitions. The focused retrieval unit file now passes 19/19 tests. The repository-wide backend unit command additionally requires configured Supabase environment variables and is therefore not a portable Phase 1 gate.

## Status-gating result

Eleven publication-withheld cases escalated because at least one controlling expected record is not production eligible. No candidate prompt causes a definitive answer from non-eligible knowledge.

## Next action

All development prompts are classified. Preserve the holdout and rerun both the maintained and non-indexed development suites after every retrieval, status, or knowledge change. Do not weaken gold expectations or status gates to preserve these scores.
